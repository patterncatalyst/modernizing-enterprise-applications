# The Six Deliberate Smells

This monolith is the "before" picture for the whole book (`_plans/build-plan.md`
section D). Six smells are planted **on purpose**, each tagged in-code with a
`SMELL[ch.NN]` comment (grep for `SMELL\[ch\.` to find every occurrence) and
mapped below to the chapter(s) that later cure it.

| # | Smell | Where it's planted | Curing chapter(s) |
|---|---|---|---|
| 1 | **Shared schema / cross-context joins** — one Postgres schema with direct JPA `@ManyToOne` FKs crossing bounded-context boundaries (`order_items` → `inventory_items`, `payments`/`shipments`/`notifications` → `orders`, `reviews` → `customers` + `inventory_items`, everything → `customers`). *(Post r02/S10: `reviews` is still in this shared schema and still FK'd to `customers`/`inventory_items`. Phase B of the review-service extraction is complete — it runs on idiomatic Quarkus (REST/Panache/CDI, no Spring-compat shim); see `examples/02-review-service/MIGRATION.md` — but the `reviews` table was deliberately left in the shared schema rather than decomposed alongside the code: the service boundary and the data boundary are separable decisions, and data decomposition for this table is deferred to ch.18/19. `examples/02-review-service` therefore still reads and writes that shared table directly against the same database; see `common/Customer.java` javadoc. Review's Java code, however, is gone from this module. Post r04/S8: the same is now true of `notifications` — its JPA entity (`notification/Notification.java`) was deleted along with the rest of the Notification context's monolith code, but the table itself stays in this shared schema, write-only history now that `examples/03-notification-service` owns its own schema; see SMELL #4 below. **Post r05/ch.19 S8 + S11: the `order_items` → `inventory_items` FK portion is CURED** — `V4__decompose_order_items_fk.sql` (S8) dropped the live DB-level FK and `order.OrderItem` now persists a denormalized sku/name/unit-price-at-order-time snapshot (a soft string reference, no JPA association); S11 then deleted the monolith's `inventory.InventoryItem` JPA entity entirely (SMELL #5 below), so there is no longer any JPA mapping onto `inventory_items` in this module at all. The `inventory_items` table itself is deliberately **kept** in the shared schema — orphaned write-only history, same treatment as `reviews`/`notifications` above, now that `examples/04-inventory-service` owns the live data and writes. **Post r06/ch.23 S9:** the same is now also true of `payments` — its JPA entity (`payment/Payment.java`) was deleted along with the rest of the Payment context's monolith code (SMELL #3 below), but the table itself stays in this shared schema, write-only history now that `examples/05-payment-service` owns its own schema and is the sole writer of live payment data.)* | `common/Customer.java`, `order/Order.java`, `order/OrderItem.java`, `shipping/Shipment.java`, `db/migration/V1__init_schema.sql`, `db/migration/V4__decompose_order_items_fk.sql` | ch.18 (shared data → owned data — inventory's FK portion cured r05/ch.19 S8; `reviews`/`notifications`/`payments` tables still kept as shared-schema history), ch.19 (CDC backfill + decommission) |
| 2 | **God `OrderService`** — one service is the single orchestration point for checkout and reaches directly into inventory, payment, shipping, and notification's services/repositories/entities. | `order/OrderService.java` | ch.26 (order extraction, hardest/last — every other extraction first removes one of this service's direct dependencies); motivates sagas (ch.23/24) |
| 3 | **One in-process ACID transaction spanning contexts** — `OrderService#placeOrder` wraps inventory decrement + order persistence + payment + shipment + notification in a single `@Transactional`, so any failure anywhere rolls back everything, everywhere. *(**Realized for payment in r06/ch.23 S9 (DRQ-047/DRQ-049) — SMELL[ch.22]'s ACID → ACD story cashed in for this context.** `OrderService#placeOrder` no longer calls payment at all — the in-process `payment.PaymentController`/`PaymentService`/`Payment`/`PaymentRepository` module is deleted along with the `payment.mode=synchronous\|choreographed` reversibility flag, and `common/exception/PaymentDeclinedException` (the exception that used to unwind this transaction on a decline) is gone too, since nothing throws it anymore. What Postgres used to give "for free" — roll back the inventory decrement when payment declines, inside one local transaction — is now rebuilt EXPLICITLY, asynchronously, cross-process: checkout persists the order `PENDING` and hands it off via the `order.placed` outbox; the payment service (`examples/05-payment-service`) captures or declines out-of-process and emits `payment.captured`/`payment.declined`; `order.OrderSagaListener#onPaymentDeclined` reacts to a decline by marking the order `PAYMENT_DECLINED` and issuing the compensating gRPC `Release` for every reserved sku — an idempotent reaction, Release-once-per-order (DRQ-051), not an implicit rollback. `OrderService#placeOrder`'s surrounding `try/catch` still exists, but its scope has narrowed: it compensates ONLY a PRE-HANDOFF failure now (a later checkout line out of stock, or the order save/outbox write itself throwing) — see that method's javadoc for why the catch and the saga reaction can never double-compensate the same reservation. The one local `@Transactional` that remains wraps just the order context's own work (customer validation, order persistence, the outbox write) — honest, since the outbox is order-owned infrastructure, not a borrowed cross-context collaborator (see smell #4's note). Shipping dispatch has also left `placeOrder`'s call path as a side effect of this step (it now fires from `OrderSagaListener#onPaymentCaptured`'s own reaction, not inline) — but Shipping remains an in-process monolith module; its own extraction is ch.24's orchestrated-saga chapter, deliberately out of scope here. The smell is therefore NOT struck through above: it is cured for payment, not yet for shipping/order, which is exactly the resume boundary ch.24/ch.26 pick up.)* | *(formerly)* `common/exception/PaymentDeclinedException.java`; *(still present)* `order/OrderService.java` (`placeOrder`, now outbox-handoff-only), `common/exception/InsufficientStockException.java`, `order/OrderSagaListener.java` (`onPaymentDeclined` — the compensating Release that replaced the deleted exception's rollback-triggering role) | ch.23 (choreographed saga — realized r06/S9), ch.24 (orchestrated saga), ch.22 (ACID → ACD — realized for payment r06/S9) |
| 4 | ~~**Synchronous notification inside the checkout transaction**~~ — **CURED in r04/S8.** The order-confirmation notification used to be sent via a direct in-process call (`notification.NotificationService#sendOrderConfirmation`), inside the same `@Transactional` as the rest of checkout, coupling checkout latency and failure domain to an orthogonal concern. `OrderService#placeOrder` now unconditionally writes an `order.placed` row to the transactional outbox (atomically, in the same transaction) instead — the reversibility flag (`notification.mode=synchronous\|outbox`) introduced for the cutover has been removed along with the synchronous branch, so outbox is the only path. Notification's controller/service/repository/entity have been removed from this module entirely; it is now served by `examples/03-notification-service` (consuming `order.placed` off Kafka, asynchronously, via its own SmallRye Reactive Messaging consumer) behind the strangler proxy, with `strangler.notification.enabled=true` as the permanent default. The underlying `notifications` table is deliberately **kept** in the shared schema (write-only history, no longer read anywhere) — true data decomposition for it is deferred to ch.18/19, same treatment as the `reviews` table in SMELL #1. | *(formerly)* `notification/NotificationService.java`, `notification/NotificationController.java`, `notification/Notification.java`, `notification/NotificationRepository.java`, `common/NotificationDto.java`; *(still present)* `order/OrderService.java` (`placeOrder`, now outbox-only), `common/Topics.java`, `common/outbox/OutboxEvent.java`, `common/outbox/OutboxRelay.java`, `common/outbox/OrderPlacedEvent.java` | ch.17 (notification extraction — transactional outbox + async event-driven consumer; cured end-to-end in r04/S8) |
| 5 | ~~**No anti-corruption layer / leaky domain model**~~ — **CURED in r05/ch.19 S11.** `OrderService` used to receive and hold a raw `InventoryItem` JPA entity straight from the monolith's own `InventoryService` (`findBySkuOrThrow`), with no DTO/contract and no translation layer at the seam. The ch.19 extraction (S4/S6/S7) replaced that in-JVM call with a synchronous **gRPC** call to the extracted `examples/04-inventory-service`, with `inventory.proto`'s strongly-typed wire vocabulary (`stock_keeping_unit`/`unit_price_cents`/`on_hand_qty`) as the real anti-corruption layer — `RemoteInventoryClient` translates every reply into plain values/records (`ReserveResult`/`StockSnapshot`); the raw proto type never leaks past that class, and the raw JPA entity no longer exists at all. S11 then **decommissioned** the monolith's local in-JVM path entirely: `InventoryController`/`InventoryService`/`InventoryItem`/`InventoryRepository` are deleted, the `inventory.mode=local\|remote` reversibility flag introduced for the S7 cutover is gone, and `OrderService#placeOrder` now reserves/releases/reads stock over gRPC **unconditionally** — there is no more leaky local path to fall back to. `GET /api/inventory` now 404s on the monolith directly (`examples/00-monolith/.../smoke/SixContextsSmokeTest#inventoryIsNoLongerServedByTheMonolith`); the public read surface is served exclusively by `examples/04-inventory-service` behind the strangler proxy's `strangler.inventory.enabled=true`. | *(formerly)* `inventory/InventoryController.java`, `inventory/InventoryService.java`, `inventory/InventoryItem.java`, `inventory/InventoryRepository.java`; *(still present)* `inventory/RemoteInventoryClient.java` (the gRPC client ACL), `order/OrderService.java` (`placeOrder`, gRPC-only), `src/main/proto/dev/patterncatalyst/inventory/v1/inventory.proto` | ch.16 (content-based routing & the ACL — realized as the gRPC proto contract rather than a Camel message translator, since the mutating Reserve/Release hot path is synchronous service-to-service, not a REST seam); ch.19 (inventory extraction — gRPC ACL cut in r05/S7, decommissioned end-to-end in r05/S11) |
| 6 | ~~**Review tangled into shared security but genuinely independent**~~ — **CURED in r02/S10.** Review had no runtime dependency on order/inventory/payment/shipping/notification (REST-only, no synchronous collaborator), yet its one authenticated endpoint was governed by the monolith's single global `SecurityFilterChain`, alongside every other context's rules. Review's controller/service/repository/entity have been removed from this module entirely; it is now served by `examples/02-review-service` (its own standalone Basic-auth/OIDC-track security config) behind the strangler proxy, with `strangler.review.enabled=true` as the permanent default. `security/SecurityConfig.java` remains in this module (harmless/vacuous — its `/api/reviews` rule no longer matches any route here) since nothing else in the monolith needs authentication yet. | *(formerly)* `security/SecurityConfig.java`, `review/ReviewController.java`, `review/Review.java`, `review/ReviewService.java` | ch.15 (Review extraction — the walking skeleton; demonstrated end-to-end in r02/S10) |

## Finding them

```sh
grep -rn 'SMELL\[ch\.' examples/00-monolith/src
```

Every smell above appears at least once in that output (smell 6's remaining
`SMELL[ch.15]` tag lives in the now-vacuous `security/SecurityConfig.java`,
since Review's own files were deleted in r02/S10). Smell 4's `SMELL[ch.17]`
tag is now gone from this module's `src` entirely — it lived only in the
deleted `notification/NotificationService.java` — so its absence from the
grep output above is itself evidence of the cure. Smell 5's `SMELL[ch.16]`
tag is likewise now gone from this module's `src` entirely — it lived only
in the deleted `inventory/InventoryService.java` (`findBySkuOrThrow`) and
the now-removed local branch of `order/OrderService.java#placeOrder` — its
absence from the grep output above is itself evidence of the cure. Smells
1–3 are exercised end-to-end by the
`checkoutReservesStockAndHandsOffToTheChoreographedSagaViaTheOutbox` test
